# 统一账号分阶段实施

## 当前进度

三个阶段已完成，并于 2026-09-06 在生产启用统一认证。详见 [生产上线记录](unified-accounts-production-release.md)。

- `server/account-store.js`：统一账号库、独立应用授权、版本控制、变更审计。
- `server/legacy-account-import.js`：旧配置到新结构的显式映射和权限快照。
- `scripts/import-legacy-accounts.js`：默认只预览，指定 `--apply` 才导入空库。
- `server/unified-session-service.js`：新会话服务，已接入网关 HTTP 登录的新模式。
- 三个后台已接入操作权限与数据范围检查；员工拥有独立入口授权。

默认 `ADMIN_AUTH_MODE=legacy`，发布代码不会自动切换现有认证。
新模式每次请求查询网关，无授权缓存或 Basic 降级。细粒度按钮、账号管理页面和
按授权生成的切换菜单已实现，已完成本地及生产 Chrome 验收。

## 数据结构与职责

独立的 `accounts.db` 位于 `ADMIN_AUTH_STATE_DIR`，与现有 `sessions.db` 分开。

| 表 | 内容 |
| --- | --- |
| `accounts` | 稳定账号 ID、唯一用户名、显示名称、密码、启用状态、全局版本 |
| `account_access` | `(account_id, app)` 唯一；应用内角色、操作权限 JSON、业务配置 JSON、启用状态、应用版本 |
| `account_audit` | 操作人、时间、动作、账号、应用、变更后版本 |

应用标识为 `invoice`、`staff`、`expense`。角色属于应用，不自动产生其他应用授权。
网关校验通用结构；业务应用必须校验自己的权限名称和配置，并在接口执行时检查。
未配置或停用的应用访问默认拒绝。账号管理能力后续单独授权，不从业务 `admin` 推导。

密码按此前约定保存在 Gateway SQLite 内，精确比较；公开查询、迁移预览、会话和
审计不包含密码。数据库文件权限为 `0600`，新状态目录为 `0700`。

账号名称、密码或启用状态更新递增全局版本，旧会话在所有应用失效。某个应用授权
更新只递增该应用版本，其他应用会话仍有效。停用后再启用不会恢复旧会话。写入要求
提供预期版本，防止管理操作互相覆盖。授权新增或版本变化后需重新登录以取得新授权。

## 首次迁移保持的行为

| 来源 | 目标应用 | 操作 | 数据范围 |
| --- | --- | --- | --- |
| 开票管理员 | invoice | 查看、附件、删除 | 全部 |
| 同一开票管理员 | staff | 查看、附件、编辑、删除、恢复 | 全部 |
| 报账管理员 | expense | 查看、附件、提交、编辑、删除、导入、查看他人批量任务 | 全部，现有六个提交渠道 |
| 报账合伙人 | expense | 查看、附件、提交 | 查看全部；提交仅原有三个合伙人渠道 |
| 报账店长 | expense | 查看、附件、提交 | 查看须同时满足本人归属和分配门店对应的店长渠道；提交仅这些渠道 |

这一步把开票和员工授权拆成两条记录，同时保留旧账号原有能力。是否取消某人的某个
后台访问，后续通过明确的人员权限表调整。迁移不会自动削减合伙人的提交能力。
`viewScope` 与 `submitScope` 分开配置，并保留渠道约束；仅使用门店约束可能扩大
同一门店下不同渠道的权限。店长本人归属必须依据服务端记录的账号 ID。

## 预览与导入

使用已有受控环境加载的旧账号配置执行，勿把真实密码写进命令行或版本库。
以下命令需在具备既有环境变量的 Gateway 项目目录执行：

```sh
npm run accounts:preview
npm run accounts:preview -- --mapping /private/path/account-mapping.json
```

默认预览不创建状态目录或数据库。退出码 `0` 表示预览可导入，`2` 表示存在身份
冲突，`1` 表示输入或存储错误。输出包括原账号来源、三个后台的权限、冲突和无密码
映射模板。同名或同密码都不会自动合并。

将预览结果的 `mapping` 对象保存为映射文件。每个旧来源必须恰好出现一次。
如明确知道两个旧管理员代表同一个人，可使用以下单组映射形式（其他来源仍须列齐）：

```json
{
  "accounts": [
    {
      "accountId": "reimbursement-admin",
      "username": "confirmed-username",
      "displayName": "管理员",
      "sources": ["invoice:invoice-admin", "reimbursement:reimbursement-admin"],
      "credentialSource": "invoice:invoice-admin"
    }
  ]
}
```

`credentialSource` 明确指定统一账号沿用哪份旧密码；多来源组必须填写。
也可以保留独立账号并显式改用户名来消除同名冲突。凡包含报账来源，必须保留其
原账号 ID；两个报账账号不能合并，防止历史记录归属被破坏。

确认映射后，首次导入命令为：

```sh
npm run accounts:preview -- --mapping /private/path/account-mapping.json --apply
```

导入在单个事务中执行，失败回滚全部账号、授权及审计写入。只允许空账号库首次导入，
重复执行不会覆盖。它不修改 `sessions.db`、业务数据、环境配置或当前登录模式。
运行账号应与服务状态目录的所有者一致；生产 `DynamicUser` 目录不要用不匹配的
所有者直接创建文件。第一阶段未在生产执行任何导入。

## 配置与发布顺序

各服务的 systemd 模板新增两层可选环境文件：

- `/etc/admin-auth-internal.env`：仅保存共享 `ADMIN_AUTH_INTERNAL_TOKEN` 和
  `ADMIN_AUTH_GATEWAY_URL=http://127.0.0.1:8790`，不在这里设置模式。
- `/etc/admin-auth-{gateway,invoice,staff,expense}-mode.env`：对应服务的
  `ADMIN_AUTH_MODE=legacy` 或 `unified`。这些文件独立于 HTTP 试用覆盖配置。

内部密钥为 32–256 位字母、数字、下划线或连字符，由受控生产配置提供。
新模式仅允许回环地址；网关启用前必须已经导入 `accounts.db`。

内部接口为 `GET /internal/authorization/{invoice|staff|expense}`，同时要求本机
连接、服务端 Bearer 密钥和有效 Cookie，修改请求还要通过同源检查。权限撤销、
网关故障、未知权限或不支持的配置都拒绝访问。开票与员工支持 `ownership: any`
和门店范围；公共表单记录没有可信提交账号，配置 `ownership: self` 会被拒绝。

先以旧模式发布新版网关（支持 staff 旧授权别名），再发布三个后台及 Nginx 员工
校验配置。这样可以逐项目发布代码并验证旧模式。
**最终启用需要在同一维护窗口协调切换网关与三个后台**；本阶段未实现混合认证。
不能只开网关新模式并期待旧模式后台继续收到 Basic 凭据。模式不一致时会拒绝
访问，不能作为无停机迁移承诺。

回退时恢复网关和受影响后台的旧模式并重启对应服务。新版网关的 staff 别名在旧
模式下仍有效；若回退到不含此别名的旧网关代码，必须同时回退 Nginx 员工配置。

快捷指令仍独立使用原有 Bearer 认证和旧配置中的归属匹配，新账号库暂不管理其
令牌和匹配关系。生产切换前需核对旧报账 ID 与快捷指令归属，不能把报账人字段
当作统一账号登录身份。历史数据不回填。

## 第三阶段：账号管理与界面

入口 `/auth/accounts` 由 Gateway 直接处理，只有新模式启用时存在。
`ADMIN_AUTH_MANAGEMENT_ACCOUNT_IDS` 是以逗号分隔的稳定账号 ID 列表，由服务器
受控配置明确授予账号管理权限，默认为空。业务角色不产生此权限，网页不能修改
该列表。管理账号即使没有任何业务后台授权，也可以直接在此入口登录。

配置示例只含占位 ID，实际 ID 必须在导入后核对：

```text
ADMIN_AUTH_MANAGEMENT_ACCOUNT_IDS=confirmed-account-id
```

将此项放入 Gateway 专用模式配置文件，不放入各业务共享配置。
页面提供账号创建、显示名称/登录名修改、重设密码、停用，以及各后台的独立授权。
新建账号默认没有业务授权；保存一个后台不会改变另一个后台的配置。角色是标识，
操作权限通过勾选配置。报账的查看和提交范围分别设置门店及渠道。
密码从不回显，重设密码输入框留空表示保持原值。修改当前管理账号后跳转重新登录；
不能停用正在使用的管理账号。新增、修改和授权写入均记录稳定操作人 ID。

管理写请求要求有效管理会话、与会话绑定的 CSRF 值、真实同源 Origin 和预期版本。
不会信任客户端 X-Original-* 来跳过同源检查。并发修改返回冲突，未知输入拒绝。
页面采用服务端 HTML 表单，无需在浏览器保存令牌或密码，支持手机单列布局。

三个后台按会话的真实应用授权展示切换入口，仅管理账号看到账号管理入口。只读
账号不会显示写操作；员工的编辑、删除、恢复及报账的编辑、删除、补录分别控制。
无切换目标时保留原页头标签和布局，禁用点击。界面限制之外保留第二阶段服务端
权限检查，旧页面或手动请求不能越权。

本地浏览器检查使用真实临时 Gateway 与业务服务，覆盖管理登录、创建账号、保存
授权、密码不回显、只读按钮、未授权菜单隐藏及 390px 手机宽度。浏览器脚本在
`integration/browser-check.js`，需通过 `AUTH_PLAYWRIGHT_MODULE` 指定本机 Playwright
模块，再运行 `npm run test:integration`；没有配置时只执行 HTTP 联调。

## 权限管理界面规则

权限管理界面以具体操作和最终生效范围为准，角色仅作为身份标签。选择权限模板会
填充权限和范围，管理员仍能在保存前调整。店长模板不会自动选择门店，必须明确
选择允许的普通报账或店长报账渠道。

“全部”是总开关：选中时所有子项同步选中；取消任一子项后显示半选状态。服务端
只根据最终子项计算范围，不接受“全部”和子项互相矛盾的含义。报账按门店展示
普通报账和店长报账矩阵，查看、提交、补录使用三套独立范围。

启用后台访问必须具备可进入该后台的基础权限。附件、编辑、删除、恢复、补录和
查看他人批量任务依赖相应查看权限；浏览器会自动联动，服务端也会拒绝绕过界面的
矛盾配置。启用的权限如果对应范围为空，同样拒绝保存。仅有报账提交权限的账号，
后台入口直接指向提交页面。

每个后台表单会实时展示最终生效的操作和范围。停用某后台时，已有配置会保留但
明确显示不生效。账号列表同时显示显示名称和登录名，详情显示不可修改的账号 ID。
重设密码和全局停用要求二次确认；管理页面不允许新登录名或新密码以空格开头或
结尾。审计记录展示状态、权限和范围的变化，不记录密码内容。


第三阶段最终本地验证：网关 52 项、开票 22 项、员工 17 项、报账 189 项、共享
入口 11 项、跨项目联调 10 项通过，报账另有 1 项原有跳过。新增界面使旧的
“仅 admin 可以切换后台”与“写权限同时控制补录”的源码断言失效，已按实际
授权行为更新；浏览器另验证实际按钮和导航。桌面和 390px 手机视口均无页面
横向溢出，数据表保留原有容器内横向滚动。截图保存在本地临时验收目录，未将
测试账号写入实际账号库。所有修改未提交、未部署，尚待生产账号映射和发布。
